bugpilot — Architecture & Code Guide

A CLI that turns a Jira bug into an AI-ready development package with a deterministic pipeline, launches a coding agent to implement the fix, and keeps a human in control of what ships.

Python 3.10+ · standard library only Legacy C++ / Qt · Jira Cloud ~22 core modules · ~6k LOC

bugpilot runs from a target product repository and writes everything it produces under .ai/<issue>/ (per-issue artifacts) and .ai_memory/bugs/ (shared memory). It never modifies product source itself; a coding agent does that, and only after a human approves.

The central idea is a clean split: the reproducible work (reading Jira, searching code, building context) is fully deterministic and runs with no model; the creative step (writing the fix) is delegated to an agent; and the decision (what to commit) stays with a person. Every boundary between these is a plain, inspectable file.

2 · Design principles

Deterministic prep, stochastic implementation

Steps 1–9 of the workflow are pure functions of their inputs — the same Jira issue produces the same package, cacheable and auditable. No LLM participates in preparation. The model is reserved for the one step that needs judgment.

Prepare, then hand off

bugpilot <ISSUE> builds the artifacts and then launches a coding agent — Claude by default, Copilot with --copilot, or none with --prepare-only. bugpilot itself never commits, pushes, merges, opens PRs, or transitions Jira; the agent stops at the commit gate. Sending email and writing a Jira comment stay opt-in and explicit.

Artifact-first

Every stage writes a file you can open and read (bug_context.md, code_search.md, search_quality.json, agent_task.md, …). The hand-off to an agent is a plain task package, not a hidden prompt — reviewable and version-controllable.

Agent-agnostic & dependency-light

Claude and Copilot consume the same package; nothing is vendor-locked. The runtime uses only the Python standard library — urllib for Jira/Graph, subprocess for git/ripgrep/agents, smtplib for email — so there is no third-party dependency surface to manage.

One credential boundary

Jira/SMTP/Graph secrets enter through config.py only. They come from environment variables first; the Jira email + token may also come from ~/.bugpilot/config.toml (written by bugpilot setup), with env always winning. SMTP/Graph secrets stay environment-only. Generated text is sanitized to redact secret-like values before it leaves the machine.

3 · The pipeline

bugpilot <ISSUE> (the default command; bug keyword optional) runs ten prepare steps in order, then launches the agent unless --prepare-only. Each step writes its own artifact and reads the previous one's output, so any step can also be run standalone.

1 doctor› 2 fetch› 3 parse› 4 keywords› 5 memory search› 6 code search› 7 git context› 8 context› 9 prompt› 10 memory add

After preparation the agent runs (by default), then the downstream lifecycle continues — each is a separate command:

agent (Claude by default)› check-results› summarize-results› review-package› memory update› notify / jira-comment› commit-plan · push-plan (human)
Orchestration

core/workflow.py::run_bug_workflow calls each step inside a try/except, marks status in workflow_status.json, and appends to execution.log. On a fresh run it cleans old artifacts first, and folds memory_search.md + git_context.md into bug_context.md (then removes those two intermediates).

The context inversion

context.py is a leaf by imports — it pulls in only json/pathlib — yet it depends on the outputs of Jira, search, memory, and git. That is the artifact-first design in miniature: coupling happens through files on disk, not through the import graph.

6 · How key parts work

6.1 Context building

context.py::build_context reads the per-issue artifacts and assembles one bug_context.md: Jira summary + parsed details, extracted keywords, a code-search summary, top related files, similar historical issues (memory), and git context. It also computes a context-quality score (0–100) from signals such as "description found", "high-value keywords found", "related files found", and "git context available" — a quick read on how much the agent has to work with.

6.2 Keywords & search confidence

Keyword extraction ranks candidates by how much they look like a code identifier, not by raw frequency — a bug report is mostly prose, so frequency would put "when"/"click" on top while the real class or function (mentioned once) sank. Identifier shape wins: camelCase with an internal hump, snake_case, qualified names (Foo::bar, a.b), and file names (widget.cpp); original case is preserved. It also extracts quoted phrases (UI/error strings), splits compounds into lower-tier expanded sub-tokens (generic parts like Widget/Dialog dropped), and boosts anything appearing in stack traces / error messages.

Search runs ripgrep per keyword and phrase (source globs only, build/vendor excluded), then ranks files. Ranking is specificity-first, not frequency: score is summed per distinct keyword with diminishing returns, so a file hitting one common name 100× can't beat a file with a couple of exact-identifier hits.

weight
exact phrase 12 · qualified Foo::bar 10 · high 6 · medium 2 · low/expanded 1; +bonus when a keyword matches the file's own name; +breadth for several distinct high-value keywords; −4 noisy path; +3 app-source path; +2 header/source pair.
confidence
High = high-value keyword in an app path or a file-name / phrase / multi-keyword match, with no noise; Medium = plausible; Low = generic keyword or noisy path.

The overall search_quality.json is High if any file is High, else Medium/Low, and is downgraded when matches are mostly noise. When confidence is Low, the generated task tells the agent not to edit on keyword matches alone. (Real-issue check: this ranking moved the actual fix file from not-in-top-10 to #1, and dropped a generic-keyword false positive from #1 to #7.)

6.3 Jira & ADF

jira.py::fetch_issue calls Jira Cloud REST v3 with Basic auth built from env credentials. HTTP errors are classified (401/403 → auth, 404 → not-found, 429 → rate-limited, …) into clear messages. Mock/demo fallback is off by default and only used with --allow-mock.

Jira Cloud stores rich text as ADF, not markdown. jira_adf.py converts ADF → Markdown for reading; jira.py::_markdown_to_adf converts our small markdown subset (headings, rules, bullets) → ADF for writing comments, so posted comments render cleanly instead of showing literal ##. jira_parse.py then extracts structured fields (repro steps, actual/expected, environment, errors) from the converted text.

6.4 Shared memory

memory.py keeps one markdown file per issue under .ai_memory/bugs/. During preparation (memory search) it scores existing entries against the current issue's keywords and surfaces similar past investigations into the context. After a fix, memory update folds the result summary back in. This is the reuse loop: solved issues make similar future ones faster and cheaper, since the agent re-investigates less.

6.5 Agent invocation

After preparation, bugpilot <ISSUE> launches Claude by default (--copilot switches to the agent; --prepare-only launches nothing). agent_runner.py builds the command from BUGPILOT_CLAUDE_COMMAND/_ARGS, resolves the real executable with shutil.which (wrapping Windows .cmd shims through cmd /c), and runs it interactively in the target repo so you can watch it. The agent reads agent_task.md, implements the smallest safe fix, writes result files, and stops at the commit gate (it posts a Jira status comment only when --jira-comment was requested).

Permissions

Default --permission-mode acceptEdits auto-accepts file edits but still prompts for shell commands. For an unattended demo, set BUGPILOT_CLAUDE_ARGS="--dangerously-skip-permissions" — understand it removes the safety net; always review the diff before committing.

6.6 Notifications

Two channels, both opt-in and built from local artifacts:

  • Jira comment — jira-comment --execute or an opted-in summarize-results posts exactly one comment (root cause + change summary, rendered as ADF). Jira then notifies watchers by email.
  • Email — notify --execute / a configured commit-plan sends via Microsoft Graph (preferred; works when the tenant disables SMTP auth) or SMTP; if neither is configured it writes a portable notification.eml to send from Outlook.

6.7 Fresh, resume & marker files

By default bug runs fresh: it calls cleanup.clean_issue_artifacts to wipe .ai/<issue>/ before rebuilding, so every run is reproducible from the Jira issue alone. --resume skips the clean and preserves prior artifacts, and --include-memory (fresh only) also drops the issue's memory entry.

Two per-run choices need to outlive a resume and standalone regeneration, so they are persisted as small marker files written once and read back by prompt_step / copilot_task_step:

developer_hint.md
--hint "…" steers the agent straight to a fix location. An explicit hint wins; otherwise a hint from a prior run is reused on resume.
jira_comment_on.flag
The pre-commit "Report Status to Jira" block is omitted by default; --jira-comment writes this marker to add it to agent_task.md. Its presence flips the generated instructions; --fresh clears it back to the default.

The same idea drives the intermediate fold: memory_search.md and git_context.md exist only long enough for context.py to absorb them into bug_context.md, then _remove_intermediate_files deletes them so the final package stays clean.

6.8 Status & failure handling

Each step is wrapped so a failure is recorded, not swallowed. _mark_step writes a per-phase verdict (pass / skipped / fail) and logging_utils.log appends a UTC-timestamped line to execution.log. On any exception, run_bug_workflow writes a final workflow_status.json and re-raises, so the CLI can point you at the log.

{
  "issue_key": "JR-12345",
  "mode": "prepare-only",
  "steps": { "doctor": "pass", "fetch": "pass", …, "agent_fix": "skipped" },
  "generated_files": ["bug_context.md", "agent_task.md", …],
  "fresh": true,
  "allow_mock": false
}

The steps map is keyed by every entry in WORKFLOW_STEPS, so status is complete even for phases a given run skipped (e.g. agent_fix in prepare-only mode). Degradation is graceful: a missing rg or git is detected via command_available and the affected step skips with a note rather than crashing the run.

7 · Safety model

The tool is deliberately constrained; outward effects are the exception, not the default.

  • Never automatic: no commit, push, merge, PR, or Jira field/status/assignee change — by bugpilot or the agent.
  • Only two Jira writes, both opt-in: one comment via jira-comment --execute, or one via summarize-results when enabled.
  • The agent runs by default (Claude), but stops at the commit gate; --prepare-only skips it. Email is opt-in. Secrets stay in the environment, except the Jira token setup saves to ~/.bugpilot/config.toml (plaintext for now, behind a replaceable seam).
  • Cleanup is scoped: clean validates the issue key and deletes only .ai/<issue>/ (and the memory file with --include-memory). It never touches product source.
  • Agent output is third-party code: the task stops at the commit gate; a person reviews and approves.
The two boundaries

The task package (deterministic → model) and the commit gate (model → human) are the enforceable control points. Both are inspectable files/steps.

9 · Configuration

Configuration is environment variables, resolved in config.py. For Jira, the friendly path is bugpilot setup, which writes ~/.bugpilot/config.toml; env vars still override it, and JIRA_BASE_URL defaults to the fixed company site.

# Jira — set by `bugpilot setup` (~/.bugpilot/config.toml), or via env:
JIRA_BASE_URL   JIRA_EMAIL   JIRA_TOKEN        # env overrides the config file
BUGPILOT_CONFIG_DIR                            # override ~/.bugpilot (tests, relocation)

# Auto Jira comment
BUGPILOT_AUTO_JIRA_COMMENT=true

# Email — Microsoft Graph (preferred) or SMTP
BUGPILOT_EMAIL_FROM   BUGPILOT_EMAIL_TO
GRAPH_TENANT_ID  GRAPH_CLIENT_ID  GRAPH_CLIENT_SECRET      # Graph
SMTP_HOST  SMTP_PORT  SMTP_USERNAME  SMTP_PASSWORD         # SMTP
SMTP_USE_STARTTLS=true   SMTP_USE_SSL=false

# Agent invocation
BUGPILOT_CLAUDE_COMMAND=claude   BUGPILOT_CLAUDE_ARGS="--permission-mode acceptEdits"
BUGPILOT_COPILOT_COMMAND=copilot BUGPILOT_COPILOT_ARGS=""
One credential boundary

Jira/SMTP/Graph secrets enter through config.py only (env, plus the Jira email/token from ~/.bugpilot/config.toml). The lone other env reads are the BUGPILOT_AUTO_JIRA_COMMENT flag in cli.py and BUGPILOT_CONFIG_DIR in user_config.py. Secrets never reach an artifact.

10 · Testing

The suite (pytest, ~228 tests) is fully deterministic and offline. External calls are mocked at the seam: urllib.request.urlopen for Jira/Graph, subprocess.run for git/ripgrep/agents, smtplib.SMTP for email. Tests use tmp_path as a throwaway repo and assert on the exact artifacts and status written. Because preparation is deterministic, most tests just run a step and diff its output.

python -m pytest -q

11 · Extending

To add a new prepare step:

  1. Write <name>_step(repo_root, issue_key) in workflow.py — read the prior artifact, write yours, call _mark_step(...) and log(...).
  2. Call it from run_bug_workflow at the right position (with a _progress event).
  3. Add the step name to WORKFLOW_STEPS in config.py so it appears in status.
  4. Register a CLI subcommand in cli.py so it can run standalone.
  5. Add a test that runs it in a tmp_path and asserts the artifact.

New service logic goes in its own core/ module and is called by the step — keep cli.py thin and side-effect-free beyond dispatch. Reads of the environment belong in config.py; a new pure helper (parsing, rendering, ranking) should stay a leaf with no bugpilot.core imports so it remains unit-testable.
